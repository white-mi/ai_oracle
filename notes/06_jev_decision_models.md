## 1. Company and model facts (founders, funding, release, versions, availability, pricing, latency, context, weights, fine-tuning, retention, cutoff)

## 2. API: exact request and response shape, SDK, limits, errors, OpenRouter

### Takeaway
One endpoint, `POST https://api.typesafe.ai/v1/systemone`, takes `{state, model, questions}` and returns `{model, answers, usage}`. The schema below was read from the generated Pydantic models in the official Python SDK (typesafe-sdk 0.7.2, MIT), so the field names are confirmed rather than inferred; limits like "max 255 options" come from docs, not the schema.

### Cited Findings
- Endpoints in the OpenAPI document (version "0.2.0"): `POST /v1/systemone` ("Answer questions about supplied content") and `GET /v1/models`; no servers block; `questions` requires at least one entry (`minProperties` 1); `ScoreQuestion.criteria` has `minItems` 1; no max constraints on questions, criteria, instructions or state are declared in the schema. [INDEPENDENT-MEASURED] — [api.typesafe.ai/openapi.json](https://api.typesafe.ai/openapi.json)
- SDK constants: `SYSTEM_ONE_PATH = "/v1/systemone"`, `MODELS_PATH = "/v1/models"`, `DEFAULT_BASE_URL = "https://api.typesafe.ai"`, `DEFAULT_MODEL = "jev-latest"`, `DEFAULT_TIMEOUT = 10.0` seconds; environment variables `TYPESAFE_API_KEY`, `TYPESAFE_BASE_URL`, `TYPESAFE_DEFAULT_MODEL`, `TYPESAFE_LOG_LEVEL`; headers `Authorization`, `Accept`, `Content-Type`, `User-Agent`, `X-TypeSafe-SDK`, `X-TypeSafe-Runtime`, `X-TypeSafe-Retry-Count`; request id returned in header `x-typesafe-request-id`; retry hints in `retry-after` and `retry-after-ms`. [INDEPENDENT-MEASURED, SDK source] — [typesafe-sdk 0.7.2 wheel](https://files.pythonhosted.org/packages/99/5e/2b97ba9b0b77612e3a480ddb60c0c0325b4809ef57a7b565341d65ef7bec/typesafe_sdk-0.7.2-py3-none-any.whl)
- Docs confirm `POST https://api.typesafe.ai/v1/systemone` with `Authorization: Bearer <API_KEY>` and `Content-Type: application/json`; keys come from `console.typesafe.ai/settings/keys` per Apidog. [VENDOR-CLAIM] — [docs API page](https://docs.typesafe.ai/api.md); [SECONDARY-ONLY] — [Apidog](https://apidog.com/blog/what-is-jev/)
- Request body (from `SystemOneRequest` in the SDK): `state` = string, object or array ("The content all questions in this request refer to"); `model` = name or alias (example "jev-latest"); `questions` = map from a name you choose to a question object. The SDK builds exactly `{"state":..., "model":..., "questions":...}` and shallow-merges any `extra_body` over it. [INDEPENDENT-MEASURED, SDK source] — [wheel](https://files.pythonhosted.org/packages/99/5e/2b97ba9b0b77612e3a480ddb60c0c0325b4809ef57a7b565341d65ef7bec/typesafe_sdk-0.7.2-py3-none-any.whl)
- Question objects (SDK wire models):
  - Noul: `{"type":"noul", "instructions"?: str|object|list, "criteria"?: {"true"?: ..., "false"?: ...}}`. Descriptions are optional; `instructions` examples include a statement ("This message contains unsolicited advertising.") as well as a question.
  - Choice: `{"type":"choice", "instructions"?: ..., "criteria": {label: description|null}}`; `criteria` is required; "A choice without a description is interpreted by its name alone."
  - Score: `{"type":"score", "instructions"?: ..., "criteria": [description, ...]}`; `criteria` is required, ordered and non-empty; "Each description's position determines its score, starting at zero."
  - In the SDK and OpenAPI, `instructions` is optional (default None) for all three, while the docs API page says it is required for each; always send it. [INDEPENDENT-MEASURED, SDK source] vs [VENDOR-CLAIM] — [wheel](https://files.pythonhosted.org/packages/99/5e/2b97ba9b0b77612e3a480ddb60c0c0325b4809ef57a7b565341d65ef7bec/typesafe_sdk-0.7.2-py3-none-any.whl); [docs API page](https://docs.typesafe.ai/api.md)
- Response body (SDK `SystemOneResponse`): `{"model": str, "answers": {name: Answer}, "usage": {"input_tokens": int, "output_tokens": int}}`. The `answers` map must be non-empty and each answer's `type` matches its question. Answer shapes:
  - Noul: `{"type":"noul","noul": float}`; `noul` is the "Probability of a yes answer or a true statement, from 0 to 1". There is no `confidence` and no `probabilities` field (the docs say "there is no separate `confidence` value for a Noul").
  - Choice: `{"type":"choice","choice": str,"confidence": float,"probabilities": {label: float}}`; "values sum to approximately 1".
  - Score: `{"type":"score","score": float,"confidence": float,"legend": {"0": ...},"probabilities": {"0": float,...}}`; `score` is "the probability-weighted average of the rubric levels" and "May fall between integer levels".
  [INDEPENDENT-MEASURED, SDK source] — [wheel](https://files.pythonhosted.org/packages/99/5e/2b97ba9b0b77612e3a480ddb60c0c0325b4809ef57a7b565341d65ef7bec/typesafe_sdk-0.7.2-py3-none-any.whl); noul semantics also [VENDOR-CLAIM] — [docs Noul page](https://docs.typesafe.ai/primitives/noul)
- SDK accessors: `response.answers[name]`, plus convenience dicts `response.nouls`, `response.choices`, `response.scores`; `ScoreAnswer.legend` and `.probabilities` are keyed by integer score; unknown future answer types are dropped with a warning (raw payload on `raw_http_response`). `response_model=` lets you parse into your own Pydantic model. [INDEPENDENT-MEASURED, SDK source] — [wheel](https://files.pythonhosted.org/packages/99/5e/2b97ba9b0b77612e3a480ddb60c0c0325b4809ef57a7b565341d65ef7bec/typesafe_sdk-0.7.2-py3-none-any.whl)
- Documented limits: "A Choice question accepts up to 255 options"; Score "up to 10" levels and "at least two levels" (docs) while the schema only requires one criterion; 64k tokens per request, 32k for state plus longest question. A maximum number of questions per call is not documented anywhere I read; public examples use 6 (a Polymarket scanner), 14 (vendor cookbook) and 15 (a swarm test) questions per call. [VENDOR-CLAIM] — [docs llms-full / API page](https://docs.typesafe.ai/api.md); [docs models page](https://docs.typesafe.ai/models.md); [SECONDARY-ONLY] — [swang666/polymarket-jev](https://github.com/swang666/polymarket-jev); [docs consistency cookbook](https://docs.typesafe.ai/cookbooks/consistency_noul_cookbook.md); [JackBeerman/swarm](https://github.com/JackBeerman/swarm)
- Questions are "evaluated in parallel and in isolation" and "Adding questions barely changes the response time"; docs recommend "atomic questions, composed in code". [VENDOR-CLAIM] — [docs introduction](https://docs.typesafe.ai/introduction.md). A comparison of open clones notes questions batched cannot see each other's answers. [SECONDARY-ONLY] — [lilting.ch](https://lilting.ch/en/articles/jev-clones-architecture-comparison)
- Confidence definitions (docs): Choice `confidence = (p_max - 1/n)/(1 - 1/n)`; Score `confidence = max(0, 1 - sum_i p_i|i - m| / MAD_unif)`; Noul `|2p - 1|`. [INDEPENDENT-MEASURED, small] — [docs Choice page](https://docs.typesafe.ai/primitives/choice.md); [OpenRouter tutorial](https://openrouter.ai/docs/guides/community/jev-tutorial); [SamuelSacco/jev-exploration #10](https://github.com/SamuelSacco/jev-exploration/issues/10)

### Inferences
- Binary decisions can be asked three ways (Noul with no confidence field, 2-option Choice, 2-level Score) and the docs themselves warn that "Noul and Choice don't agree" across question types and thresholds are not portable; for a binary Choice with p_max = 0.90 the API `confidence` is only 0.80, so "confidence >= 0.9" in the API means p_max >= 0.95, whereas academic studies usually threshold the top probability itself. Anyone comparing a "confidence >= 0.9" result across sources must check which definition was used.
- The 0.01 output grid and frequent exact zeros mean ties, no usable ranking inside the saturated region, and log-loss or Brier terms that can blow up when a correct answer receives 0.00; apply clipping before scoring.
- State size matters: with 32k tokens for state plus the longest question, long resolution sources need pre-filtering in code (the docs also list large noisy state as a failure mode).

### Gaps
- Maximum number of questions per call, maximum question and state length in characters, and whether Score really enforces the documented 2-level minimum are unknown (OpenAPI says 1).
- I could not verify directly (no key, direct curl blocked) whether the direct API returns the same 0.01 rounding as the gateways, or whether Noul is clamped.
- The OpenRouter `api/v1/systemone` surface is named once in a summarized page; I did not see an example using it.
- Exact docs wording was read through a summarizer; where precision matters (limits, rate limits) re-read https://docs.typesafe.ai/models.md and https://docs.typesafe.ai/api.md in a browser.

## 3. Training method "RLCD" (Reinforcement Learning for Calibrated Decisions): disclosed versus undisclosed

### Takeaway
TypeSafe discloses only the name and the goal: a new architecture, a new sampler and RLCD, with the objective that stated probabilities match outcome frequencies in groups. Architecture, sampler design, objective (Brier/log loss?), data (synthetic or real) and any ablation are not disclosed in the docs I read; secondary sources assert "proper scoring rules" and "100% synthetic data" without a primary I could find.

### Cited Findings
- Homepage disclosure: "new architecture, a new sampler, and a new training algorithm: Reinforcement Learning for Calibrated Decisions (RLCD)". [VENDOR-CLAIM] — [typesafe.ai](https://typesafe.ai/)
- Docs primer: "Reinforcement learning for calibrated decisions trains TypeSafe to return decisions and calibrated probabilities instead of generated text"; objective phrased as "Higher probability should correspond to a greater chance that the answer is correct"; "Outcomes assigned a probability of 0.2 should occur about 20% of the time"; caveat "These rates describe groups of predictions, not a guarantee about any single answer." The primer explains why RLCD rather than RLHF or RLVR but does not specify scoring rules, whether data are synthetic, architecture or sampling. [VENDOR-CLAIM] — [docs primer](https://docs.typesafe.ai/introduction/machine-learning-primer.md)
- System One page: probabilities are "optimized against outcomes to reflect uncertainty"; "Calibration is measured across groups of predictions; it does not guarantee that an individual answer is correct"; models "do not write replies, produce code, or generate explanations of their reasoning". [VENDOR-CLAIM] — [docs System One page](https://docs.typesafe.ai/concepts/system-one)
- Company framing per a wiki: RLHF "optimizes for the text that a human rater prefers" and RLVR does not fit most real-world judgement tasks; no peer-reviewed RLCD paper existed at the source date. [SECONDARY-ONLY] — [aiwiki.ai](https://aiwiki.ai/wiki/typesafe_ai/raw)
- Unsupported specifics circulating: that RLCD uses "proper scoring rules (log loss, Brier score)" and that the model was "trained on 100% synthetic data" (listed as an unproven claim) both come from one critical blog, without a primary link; the docs primer explicitly does not state either. [SECONDARY-ONLY, conflicting with docs silence] — [AgentConn](https://agentconn.com/blog/jev-typesafe-new-agent-layer-if-calibration-holds/)
- TypeSafe has published "zero reliability diagrams, no ECE measurements, no calibration ablations, no comparison of RLCD versus baseline training methods" (assessment by a critic, consistent with the docs confidence page which contains no ECE data). [SECONDARY-ONLY] — [AgentConn](https://agentconn.com/blog/jev-typesafe-new-agent-layer-if-calibration-holds/); [docs confidence page](https://docs.typesafe.ai/confidence.md)
- Independent attempt at an open RLCD-style model: researchers trained a Qwen3-0.6B "RLCD" model; it reached median ECE 0.128 but "median Brier score of 0.662 and coverage-accuracy area of 0.505 suggest a confidence signal with almost no ranking value", showing calibration error alone can look acceptable while the confidence is useless for ranking. [INDEPENDENT-MEASURED] — [arXiv 2609.24574 (HTML)](https://arxiv.org/html/2609.24574v1)
- Output-head audit: an arXiv paper on constrained decision heads proves "masked renormalization guarantees schema validity" (type-error rate 0% in all conditions) and treats the hosted Jev as a black box. It does not reveal Jev internals. [INDEPENDENT-MEASURED] — [arXiv 2609.26758 (HTML)](https://arxiv.org/html/2609.26758v1)
- Open clones use very different recipes (frozen LLM option logits, LoRA plus readout heads, ModernBERT scoring heads, NLI-style scoring), which shows the "typed readout" idea is reproducible without knowing Jev's internals. [SECONDARY-ONLY] — [lilting.ch](https://lilting.ch/en/articles/jev-clones-architecture-comparison); [awesome-system-one](https://github.com/yanng981/awesome-system-one)

### Inferences
- Because architecture, data and objective are all undisclosed, any claim that RLCD itself causes better calibration is untestable from outside; the available evidence says Jev's calibration is mediocre-to-good on classification and unproven elsewhere (see section 8).
- "Calibrated" is a training goal with group-level semantics; for a resolver, a per-question-type calibration map fitted on your own labeled items is the only defensible route.

### Gaps
- No primary source for the objective (scoring rule) or data (synthetic or not); TypeSafe's blog and Almeida's launch post could not be read.
- No peer-reviewed or technical-report description of the architecture or "parallel sampler".

## 4. Documented failure modes (the nine "jagged edges" of Jev 1.13)

### Takeaway
TypeSafe's docs page "Jev 1.13 jaggedness" lists nine failure modes: literal reading, math and numbers, date and time comparison, indirection, large state full of irrelevant detail, adversarial content, contradictory instructions and criteria, choice option order, and generation. Several of them (dates, injection, large noisy evidence, option order) bite directly on a prediction-market resolver.

### Cited Findings
- The page states nine failure modes for jev-1.13 (page https://docs.typesafe.ai/model-jaggedness/jev-1.13.md). Items, with the fragments returned inside quotation marks by the fetch tool; the rest is paraphrase of the page: [VENDOR-CLAIM] — [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md)
  1. Literal Reading: the model "answers the question you wrote, not the one you meant"; state exact conditions and boundary cases.
  2. Math and Numbers: "Jev is not a calculator. We strongly recommend implementing any mathematical logic in code."; counting is unreliable, numeric representations work poorly (prefer semantic descriptions), numerical calibration weak when interpolating between score levels.
  3. Date and Time Comparison: the model "reads dates as text, not as ordered quantities"; split extraction (model) from arithmetic (code), use enumerated options.
  4. Indirection: several logical hops reduce accuracy; write instructions "as directly as possible" and name the relevant state.
  5. Large State Full of Irrelevant Detail: unrelated content distracts; filter in code and send only needed fields.
  6. Adversarial Content: the model does not treat data as hostile by default, so injected instructions or misleading framings can influence answers; test before deployment.
  7. Contradictory Instructions and Criteria: misaligned instructions and criteria confuse the model; treat criteria as extensions of instructions.
  8. Choice Option Order: the model "leans toward the option that comes first" in some cases; reorder options and check consistency.
  9. Generation: Jev "isn't trained for text generation" and does poorly when forced to generate; prefer extraction.
- Other documented limits: text only; English primary; no generation; "not agents. It does not generate code or choose its own next action"; confidence describes groups of predictions. [VENDOR-CLAIM] — [docs System One page](https://docs.typesafe.ai/concepts/system-one); [docs llms-full](https://docs.typesafe.ai/llms-full.txt)
- Independent confirmations: a Polymarket repo documents that Jev "degrades with irrelevant context" and that `answerable` was 0.27 without a research brief and 0.78 with evidence [INDEPENDENT-MEASURED, hobbyist] — [markusbug/jevymarket](https://github.com/markusbug/jevymarket); a swarm test says "It reads literally" and "It is not a forecaster" [INDEPENDENT-MEASURED, hobbyist] — [JackBeerman/swarm](https://github.com/JackBeerman/swarm); a judge study finds weakness where "the verdict must be derived" (math, code, logic) [INDEPENDENT-MEASURED] — [arXiv 2609.26550](https://arxiv.org/abs/2609.26550); option-name and option-order sensitivity is quantified in section 8.
- Aggregator reports of failures beyond the nine: a Russian NLI drop (88.3% to 77.3%), 0.79 confidence on unanswerable KoBBQ items, and "fair die" probabilities averaging 83% against a true 17%. [SECONDARY-ONLY] — [xbill](https://dev.to/aws-builders/jev-after-eight-days-of-independent-tests-level-with-mid-price-llms-behind-the-frontier-1c60)

### Inferences
- For a resolver: (a) never ask Jev to compare a market's deadline with an event date; compute it in code and pass a precomputed field; (b) strip or screen scraped pages for injected instructions (TypeSafe's own RAG cookbook adds a `contains_prompt_injection` Noul for this); (c) randomize or neutralize option labels and order and test invariance.

### Gaps
- I did not obtain the page as raw text; the numbering and quotes are from a summarizing fetcher (two fragments in quotation marks are direct strings from it). Re-read the page before quoting verbatim in the final report.

## 5. Independent evaluations (who, n, task, numbers, URL)

### Takeaway
Within three weeks there is already a broad set of third-party tests, and they agree on a consistent picture: Jev is very cheap and fast, about 6 to 12 macro-F1 points behind the best frontier LLM on harder or ambiguous tasks, level with TF-IDF logistic regression or a fine-tuned small encoder on easy ones, and its confidence is usable but only moderately calibrated (median ECE roughly 0.07 to 0.16, worse on some multi-class and out-of-distribution tasks). The vendor's own headline workflow evals (67.8%) use LLM-consensus labels and unnamed or flagship comparators.

### Inferences
- Everything the literature supports for resolution is the reading-comprehension variant ("has this already happened per these rules and this evidence?"), where Jev behaves like an entailment/NLI-style classifier; the only forecasting-type evidence says it adds no skill beyond an LLM and does not beat the market price.
- The swang666 design (separate Noul for "met" and "precluded", a Choice for stance, Score rubrics for directness, rule ambiguity and source authority, all arithmetic in code, no price in state) is the best available prior art to reproduce, but it has no published results, so it is a design reference and not evidence of accuracy.
- Papers using Jev share a pattern: Jev as a cheap first-pass with confidence-gated escalation (REFLEX, JEV-as-a-Judge, social-science annotation). This is exactly the structure a "confidence signal for a downstream resolver" would take.

### Gaps
- No paper, preprint or write-up of Jev on resolved prediction-market outcomes with Brier or log-loss or calibration curves; the repos have either no results or a negative result on a different task (price forecasting).
- 6G paper's submission date and the REFLEX/Jev-Mem full-text limitations were only partly visible to me.
- The 14-item checklist of arXiv 2609.32160 is unread.

## 7. Open alternatives and competitors

### Takeaway
A dozen open or semi-open "System One" clones appeared within days (Laya, kev, Decider, Von, Bespoke Nimble, SemIf/OpenJev, AnyJev, NanoJev, Tev1, GLiNER2.5-Decide and others), plus a closed rival (Fastino GLiDE) and the classic alternatives (TF-IDF models, fine-tuned encoders, NLI cross-encoders, LLM label-probability readouts). Almost every head-to-head with Jev was run by the clone's own authors on their own subsets; independent comparisons are sparse and generally put clones below Jev, though a plain LLM label-probability read is close.

### Inferences
- For a resolver study the realistic comparison set is: (1) Jev, (2) an open decision model you can run locally and calibrate (GLiNER2.5-Decide, Laya, kev), (3) a plain LLM that returns logprobs or a verbalized probability for a supports/contradicts/insufficient label, (4) an NLI cross-encoder, (5) a small supervised encoder trained on labeled resolutions. No published study compares NLI cross-encoders to Jev on evidence-based verification.
- Because Jev has no open weights, it cannot be calibrated at the logit level or audited; the clones can, which matters if the experiment needs reproducibility beyond the vendor's API lifetime.

### Gaps
- No independent, like-for-like comparison of Jev with GLiNER2.5-Decide, kev or Laya on the same human-labeled set; Fastino's and the clone authors' numbers use their own subsets.
- NLI cross-encoders and classic fact-verification models: no Jev comparison found.
- License of Bespoke Nimble is unstated in the catalogue; Tev1 weights licence pending.

## 8. Critical perspectives: "just a classifier?", calibration beyond classification, wording sensitivity

### Takeaway
Independent authors call Jev a "commercial classification model" and "a very good fast classifier", and the 28-paper audit finds no accuracy advantage from the typed readout itself; calibration evidence beyond classification is thin and mixed (decent pooled calibration, poor per-task calibration, bad on synthetic distributions, negative for forecasting). Jev is measurably sensitive to option names, option order and question context, and moderately to run-to-run noise.

### Cited Findings
- Framing as a classifier: Deußer et al. open with "Jev is a commercial classification model from TypeSafe AI designed for non-generative tasks" [INDEPENDENT-MEASURED] — [arXiv 2609.37647](https://arxiv.org/abs/2609.37647); Ibrahim and Zaki call it "the first commercial decision model" in "a new model class built for categorical question answering" and recommend it as "a first step in the annotation pipeline" [INDEPENDENT-MEASURED] — [arXiv 2609.24574](https://arxiv.org/html/2609.24574v1); a critique concludes that without published calibration evidence Jev is "a very good fast classifier" competing with fine-tuned encoders and rules, not a new category, and that it "has not yet earned trust in its probabilities" [SECONDARY-ONLY, opinion] — [AgentConn](https://agentconn.com/blog/jev-typesafe-new-agent-layer-if-calibration-holds/). TypeSafe's own docs say the models are "not agents" and do not generate explanations. [VENDOR-CLAIM] — [docs System One page](https://docs.typesafe.ai/concepts/system-one)
- Typed-readout skepticism: "the typed readout itself has not shown an independent accuracy advantage over comparable label-probability readouts". [INDEPENDENT-MEASURED] — [arXiv 2609.32160](https://arxiv.org/abs/2609.32160)
- What the critic says would settle calibration: reliability diagrams and ECE per task class, held-out non-synthetic production datasets, variance across paraphrases and option permutations, and an ablation separating RLCD from the architecture and data; it also quotes TypeSafe as admitting "We can't prove it isn't subsidized" about pricing, and reports a Reddit user's ECE of 0.046 on scam job ads, where at 0.9 confidence the model "acts on 8 ads and catches 7 of 53 scams". [SECONDARY-ONLY] — [AgentConn](https://agentconn.com/blog/jev-typesafe-new-agent-layer-if-calibration-holds/)
- Calibration evidence outside plain classification: (a) alignment-failure detection: pooled ECE 0.047 versus per-benchmark median ECE 0.168, with strong AUROC (median 0.886) [INDEPENDENT-MEASURED] — [arXiv 2609.29429](https://arxiv.org/html/2609.29429v1); (b) social-science constructs: median ECE 0.157, three frontier LLMs at 0.066, empathy ECE 0.538 [INDEPENDENT-MEASURED] — [arXiv 2609.24574](https://arxiv.org/html/2609.24574v1); (c) legal NLI: Jev 77.38% versus 83.21% top, with more unstable correctness under reordering [INDEPENDENT-MEASURED] — [arXiv 2609.27678](https://arxiv.org/html/2609.27678v1); (d) synthetic physical distributions: mean TV 0.518 versus 0.546 random [INDEPENDENT-MEASURED, blog] — [Maximum Effort](https://maximumeffort.substack.com/p/jev-is-poorly-calibrated); (e) forecasting prediction-market prices: Brier worse than the market midpoint in every arm [INDEPENDENT-MEASURED, single author] — [freqpred PR #104](https://github.com/ostersc/freqpred/pull/104); (f) a live scan where the model's probabilities were under half as dispersed as the book's and violated complementarity [INDEPENDENT-MEASURED, hobbyist] — [swang666/polymarket-jev](https://github.com/swang666/polymarket-jev). Overconfidence on "unknown/unanswerable" items (0.79 on KoBBQ) is reported by an aggregator. [SECONDARY-ONLY] — [xbill](https://dev.to/aws-builders/jev-after-eight-days-of-independent-tests-level-with-mid-price-llms-behind-the-frontier-1c60)
- Wording and structure sensitivity:
  - Option names: swapping the rubric behind "no" and "yes" changed 32.50% of hosted-Jev answers versus 2.08% for neutral 0/1 labels (test-retest floor 1.33%); on the open encoder read-outs the effect was far larger (AUROC .9376 to .2315). Recommendation: use neutral option identifiers with the meaning in the rubric text. [INDEPENDENT-MEASURED] — [arXiv 2609.26758](https://arxiv.org/html/2609.26758v1)
  - Question wording (generic detection): "question wording matters little"; best targeted wording adds only +0.006 AUROC (CI includes 0), but context supplied matters, and the answer type matters (Score beat Noul on 19 of 31 benchmarks; argmax loses to soft probabilities). [INDEPENDENT-MEASURED] — [arXiv 2609.29429](https://arxiv.org/html/2609.29429v1)
  - Decomposition framing: single phishing question 62.6% versus five decomposed questions 95.0%. [INDEPENDENT-MEASURED] — [beri.net](https://www.beri.net/article/typesafe-jev-typed-decision-model-calibration-decomposition-shadow-eval)
  - Option order and output order: vendor-documented bias toward the first option; a tweet reported that "ORDER of choices DRASTICALLY changes output probs"; the legal paper varies requested outputs and output order and finds individual decisions change even where aggregate accuracy is the same. [VENDOR-CLAIM] — [docs jaggedness page](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md); [SECONDARY-ONLY] — [AgentConn](https://agentconn.com/blog/jev-typesafe-new-agent-layer-if-calibration-holds/); [INDEPENDENT-MEASURED] — [arXiv 2609.27678](https://arxiv.org/html/2609.27678v1)
  - Question design in Polymarket use: "question design proved critical"; "calibration reflects question quality, not predictive accuracy". [INDEPENDENT-MEASURED, hobbyist] — [JackBeerman/swarm](https://github.com/JackBeerman/swarm)
- Run-to-run noise: 2.2% of phishing labels flipped between two identical passes [SECONDARY-ONLY] — [xbill review](https://github.com/xbill9/gemma4-dev/blob/main/jev/reports/Jev%20independent%20evidence%20review.md); hosted test-retest floor 1.33% [INDEPENDENT-MEASURED] — [arXiv 2609.26758](https://arxiv.org/html/2609.26758v1); vendor cookbook SD 0.0102, with up to a 0.10 range on the most uncertain item over 15 draws [VENDOR-CLAIM] — [docs consistency cookbook](https://docs.typesafe.ai/cookbooks/consistency_noul_cookbook.md); Noul moved about 0.02 on repeats [INDEPENDENT-MEASURED, hobbyist] — [JackBeerman/swarm](https://github.com/JackBeerman/swarm).
- Quantization risk: one OpenBookQA item got probability 0.00 on the correct option while the model reported confidence 0.99; the issue author says this "cannot be repaired by temperature scaling". [INDEPENDENT-MEASURED, small] — [SamuelSacco/jev-exploration #10](https://github.com/SamuelSacco/jev-exploration/issues/10)
- Calibration fixes: reported gains from a two-parameter or temperature refit on own labels (civil_comments ECE from 0.16-0.21 to under 0.025; social-science median 0.157 to 0.121 after temperature 2.661; Platt scaling on crash narratives to 0.0069). [SECONDARY-ONLY] — [xbill review](https://github.com/xbill9/gemma4-dev/blob/main/jev/reports/Jev%20independent%20evidence%20review.md)
- TypeSafe's own caution: calibration is group-level; thresholds "depend on your domain and the performance of the model for your use case". [VENDOR-CLAIM] — [docs confidence page](https://docs.typesafe.ai/confidence.md)

### Inferences
- For a resolver, "Jev is just a fast zero-shot NLI/classification head with an unusual API" is the safest working hypothesis; evidence for it is strong, evidence against it is absent. The valuable property (if it holds) is a cheap probability for "does this evidence satisfy this rule", suitable for triage and escalation, not for final adjudication of hard or ambiguous cases.
- The big risk factors for resolution specifically are: ambiguity of resolution rules (literal reading), temporal conditions (dates as text), and adversarial or noisy web evidence; all three are on the documented failure list.
- Any claim that Jev's probability is "calibrated" for this domain must be backed by your own reliability diagram with sample sizes per bin, a risk-coverage curve, and name/order/paraphrase invariance numbers.

### Gaps
- No evaluation of calibration on evidence-conditioned, rule-conditioned verification tasks (FEVER-like, ContractNLI is the nearest) with Brier/ECE reported for Jev; no study of long evidence (near the 32k limit).
- The 14-item checklist from the 28-paper audit is not read.

### Inferences
**What an experimenter must check on day one**
1. Call `GET /v1/models` and log names and `release_date`; pin `jev-1.13.0`; store `response.model`, `x-typesafe-request-id`, SDK version (0.7.2) and the API version on every call; test whether `jev-latest` changes during the study.
2. Capture raw JSON from the direct API and from any gateway you use: check probability decimals (0.01 grid?), exact 0 and 1 frequency, Noul min and max, and whether Noul or Choice values saturate; decide clipping for Brier and log loss before looking at labels.
3. Determinism: send the same request 20 times (and with a distinct `uid`-style field) and record spread; set the minimum detectable effect accordingly; decide how to aggregate repeats.
4. Invariance tests before any accuracy claim: neutral option labels versus semantic labels, polarity swap, option permutations, paraphrased instructions, and criteria-text variants; report flip rates (the hosted baseline is 1.33% test-retest and 32.50% for a polarity swap).
5. Define the question as evidence-conditioned reading ("does this evidence state that the resolution condition has already been met under these rules?") with a Choice that includes `insufficient`/`says_nothing` and a separate Noul for `precluded`; keep "will X happen?" only as a labeled negative-control arm (the prior forecasting test found no skill beyond an LLM).
6. State design: send only the resolution rules and the relevant evidence (hard limit 32k tokens for state plus the longest question); precompute all dates, deadlines and numeric comparisons in code; do not include market prices in state; add an injection-detection Noul and screen scraped text.
7. Which "confidence": decide whether you threshold the API `confidence` (normalized, e.g. 0.8 for a binary Choice at p = 0.90), the raw top probability, or `|2p-1|` for Noul; thresholds are not portable across question types.
8. Calibrate on your own labels: collect at least 50 to a few hundred labeled resolutions first, fit temperature or Platt per question type, then report reliability diagrams with per-bin counts, Brier/log loss, risk-coverage curves and the accuracy at your chosen threshold (not ECE alone).
9. Baselines run on the same items: an LLM with logprobs or verbalized probability for the same label set, an NLI cross-encoder, one open decision model (GLiNER2.5-Decide, Laya or kev), and a small fine-tuned encoder; pre-register metrics and thresholds.
10. Contamination control: no knowledge cutoff or data description is published, so use items that resolve after 2026-09-15 or private items, and run an evidence-free control (the `answerable` signal rose from 0.27 to 0.78 when evidence was added in one repo).
11. Operational: confirm actual rate limits against the two conflicting figures, handle 429 and 529 (SDK default 2 retries, 10 s timeout), check ZDR and data-processing terms if resolution content is sensitive, and confirm the language mix is English (non-English is documented as lower accuracy).
12. Budget: at $0.042 per 1M input tokens a 5,000-token state costs about $0.00021 per question set; confirm via `usage` rather than assuming, since extra questions add tokens and the OpenRouter sample reported 70 output tokens at no charge.

### Gaps
- The experiment-design items above are my synthesis from the cited findings, not claims from any single source; thresholds such as 0.8 or 0.9 are used by vendor cookbooks as illustrations and are explicitly "not calibrated defaults".
- Whether any independent party has measured Jev's behavior on lengthy evidence, adversarial evidence, or rule-conditioned resolution remains unknown as of 2026-10-05.
